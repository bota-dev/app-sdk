## Flutter Android Finding

The public plugin required `flutterSdkPath` or `BOTA_FLUTTER_HOME` even though
Flutter had written its SDK path into the application's `local.properties`.
The local consumer gate exported the test variable, hiding this normal-install
failure. The immutable public beta can be built using:

```bash
BOTA_FLUTTER_HOME=/path/to/flutter flutter build apk --release
```

Source fix `b797aa2` reads `flutter.sdk` with Java `Properties`, then falls back
to `FLUTTER_ROOT`, while retaining explicit standalone-test overrides. The
consumer gate now unsets both environment variables during Android compilation.
The same failed consumer passed after applying only the Gradle lookup fix in a
disposable plugin copy. That is source-fix evidence, not evidence of a changed
public beta. A subsequent synchronized release is required to remove the
workaround for registry consumers.

Source verification after the fix:

- `tools/flutter/test-consumers.sh`: fresh Android and iOS release builds passed;
  the Android invocation had neither Flutter environment override.
- `tools/flutter/test-android-adapter.sh`: passed.
- `npm run flutter:verify`: package checks, analysis, and all 86 Dart tests passed.
- `npm run test:tooling`: 104 tests passed.
- `npm run test:release`: 92 tests passed on the unchanged rerun. The first run
  had one timing-sensitive failure in `reports emulator output when the process
  exits before ADB connects`, which reported its timeout diagnostic instead.
  This unrelated test was not changed or hidden.
- `git diff --check`: passed. Fix received a self-review, not an independent review.

## Reproduction Notes

Use Node 22, npm 12.0.2, RN 0.86.3, React 19.2.3, CocoaPods 1.16.2, JDK 17,
and Flutter 3.47.2/Dart 3.13.2. Install exact public package versions in disposable
applications; do not point their SDK dependencies at monorepo source. Web used
`tests/consumers/web-vite` with the public tarball. RN used the adapter fixtures
with paths redirected to an ordinary consumer's installed `node_modules` and
Maven Central. Flutter used generated iOS/Android scaffolds, maintained example
files and permissions, and an exact hosted pub.dev dependency without overrides.

The RN Android fixture verifies the adapter AAR, not an end-user APK; an initial
attempt to assemble its minimal application lacked generated autolinking input.
The iOS harness also needed canonical filesystem paths. These fixture issues
did not modify installed SDK bytes. Xcode initially stalled in its Keychain
authorization provider before downloading the public binary; package resolution
succeeded with `-packageAuthorizationProvider netrc`, without changing package
URLs, checksums, signature checks, or credential-store settings.

No physical device, Demo, or Bota One acceptance is claimed. The ordinary Flutter
Android install gate remains open until the source fix is published and tested
again from the registry. New-name OIDC upload proof also remains a future-release
gate. No new release version, registry access grant, or app rollout occurred.
