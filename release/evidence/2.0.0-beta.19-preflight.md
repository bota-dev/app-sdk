# Beta.19 transfer and lifecycle preparation

This is an unpublished synchronized SDK candidate under the existing package
identities, including `@bota.dev/react-native-app-sdk/runtime`. Beta.18 remains
the public baseline. No existing artifact or tag is replaced.

## Reproduction and correction

The beta.18 Android observation received 400 consecutive 500-byte DATA payloads
while 142 appends reported durable completion. One further append was submitted;
the next 256 packets filled the bounded pending queue and packet 399 triggered
`integrity_failed` before EOF or CRC verification. START/STOP passed, while SDK
cleanup returned `operation_in_progress`. A separate reconnect failed on a late
scan callback while StopScan was pending. Actual retained system GATT ownership
was not established. See the dated
[physical review](../../docs/parity/react-native-runtime.md#october-14-android-physical-follow-up-october-15-utc).

The exact old Rust source plus new regressions was captured at
`a6c8a73636f40bef184e5bc9bc508119a2840b9d`.
[Linux regression run](https://github.com/bota-dev/app-sdk/actions/runs/38670790271)
fails at the expected backlog and late-scan assertions. Windows Application
Control blocks local Rust build-script executables; it is not bypassed.

Corrections in this candidate:

- Shared Rust coalesces already-buffered contiguous legacy DATA into appends
  capped at 32 KiB, preserving the 256-packet/128 KiB FIFO and checkpointing the
  batch sequence only after durable append completion.
- JS terminal effects wait for submitted work to settle before reusing file
  resources. Unsubmitted normal effects are retired; genuine cleanup errors and
  external file ownership remain fenced.
- StopScan joins scan startup and subscription removal. Rust ignores only exact
  retired scan/timer callbacks until stop completes; fresh serial verification
  and foreign-request rejection remain required.

Focused JS regressions and strict types pass. The source changes retain existing
version 1 OS ports and need no new installed native capability for the generated
route. Candidate checks and the bounded Android results below establish specific
source and lifecycle behavior. Exact final integration CI, full normal-app
recording acceptance and publication remain separate gates.

## Normal application follow-up, October 15

With the structured busy-read guard in place, One's normal device screen remains
connected/Idle. Normal Start/Stop succeeds and the normal home flow attempts sync.
The resulting retained local file is 228,989 bytes; a read-only on-phone size/SHA
check matches its queue metadata. The new task remains pending/retry 2 after two
upload failures reported as `SDK OS port: cancelled`. The original failed/retry-0
task and cloud pointer remain protected. One is stopped after verified Stop to
avoid further automatic attempts during diagnosis. A local file alone does not
prove cloud commitment or device cleanup.

Normal Demo Start/Stop, pending-file Sync and graceful disconnect are exercised.
The UI returns to Idle, but no new synced cloud recording is verified; the cause
of its absent result remains open. Neither app has complete physical acceptance.

An actual SDK/app-port fixture reproduces a diagnostic defect: when progress
validation fails, the SDK aborts its upload child context, and the strict HTTP
port's cancellation rejection masks that original failure. `JsRecordingUploads`
now joins the same HTTP work and preserves the recorded progress failure on
rejection. Independent cancellation still propagates. All 12 upload tests and
strict SDK types pass. A separate actual generated-core/client/queue/app-port
fixture accepts ordinary monotonic 228,989-byte progress with one provider,
one upload and one completion; a retired transfer signal is not inherited.
These fixtures do not establish the physical cancellation cause.

The subsequent normal restart retry at 17:16 UTC reaches no upload-file port
event and leaves the new task pending/retry 3. Exact scoped read-only file stats
show that `recording/<task.id>` names a different, empty file created at that
retry, while the actual retained 228,989-byte file stays intact. The managed
transfer previously used an independent UUID sink and `task_...` queue ID;
restart lookup requires their logical identity to match. New transfers now use
the existing opaque sink UUID as the task ID. The persisted task then supplies
the exact original file identity after process loss, with existing Rust queue
admission unchanged. This adds no OS-port contract or arbitrary path reopening.
The older retained task lacks that sink identity and is preserved without an
automatic migration; this correction does not recover it or explain the earlier
same-runtime cancellation. Both apps also guard their normal preparation before
cloud create: a retained recording reuses its exact scoped cloud pointer, while
ambiguous, foreign-scope or local-less retained work refuses a new create.

## Independent source review

A reviewer who did not author the reconnect correction found no actionable
issue in the source at `78f6f23`. The permitted late callbacks are confined to
`StoppingScan`: the scan request must match, and timer callbacks must match both
request and timer IDs. They cannot replace the selected candidate or start IO;
the IDs retire on the matching StopScan completion. Connection still verifies
the peripheral, discovers services and reads the exact GATT serial before
persisting trusted identity. Existing wrong-serial tests retain disconnect and
probe behavior.

The same review independently runs the focused JS startup-join regression.
It holds scan registration unresolved after a synchronous
candidate callback and verifies that StopScan acknowledgment and Connect wait
for registration and subscription removal. BLE PLX also disables its callback
before removal. An additional independent executor/generated reconnect run
passes 27/27. These controlled fixtures and the two candidate physical connections
do not establish normal-app reconnect stability under its polling workload.
