## Design review

The [source review](../../docs/parity/upload-recovery.md#october-8-pending-completion-recovery-unpublished-source) describes the controlled regressions. The authoritative Upload Management §1.1 assigns App-mediated recovery to the SDK and keeps backend verification asynchronous; cloud acknowledgment and device cleanup remain distinct durable phases.

| Requirement | Implementation and evidence | Status / remaining verification |
| --- | --- | --- |
| Recover exact pending completion under the original identity/evidence | Only `425` with `upload_verification_pending` enters 1–2 second jittered completion polling; scoped callbacks, cancellation and two-minute/120-poll bounds are tested | matched at callback boundary; host HTTP timeout remains required |
| Preserve byte-upload progress across restart without resending pending bytes | `completionPending` is committed after PUT and survives Android/Apple journal persistence; queue restart/lost-response tests skip PUT | matched in controlled/hosted tests; PUT-to-journal crash window and physical power loss remain unverified |
| Pending verification does not exhaust integrity repair budget | Budget exhaustion parks the queue for 30 seconds without increasing the repair retry count; explicit authenticated integrity failure clears the phase for repair | matched in controlled queue tests |
| Existing wire evidence accepts canonical safe decimal size strings | Matching number/string values pass; malformed/unsafe or mismatched values retain sources | matched in 73 affected host/API/v2 tests and exact hosted CI |
| Cleanup only after acknowledged commitment under the same owner | Existing identity/account/cancellation fences and native release-before-foreground CONFIRM ordering remain | matched in controlled lifecycle tests; broad physical interruption and cross-channel identity remain partial |
| Preserve managed encrypted-v2 receipt contract and direct retry ownership | No v2 signed receipt, Rust verification or firmware retry change | matched for unchanged source scope; this compatibility fix adds no direct-channel hardware claim |
| Publish exact source artifacts with public install readiness | Tag-bound promotion, protected approval, public native consumers and Flutter file-inventory verification | matched in the exact protected release and independent public reads |

The supervised Android test recovered the retained legacy recording with an unpublished source-overlay build and separately completed one fresh canonical encrypted-v2 capture with an empty SDK/device pending catalog. Those observations are candidate evidence. They do not prove a genuine public-beta.14 application install, independent signed-receipt inspection, measured physical PUT count, Apple hardware recovery, arbitrary OS scheduling or long-file performance. New native application binaries remain required; an OTA JavaScript update alone does not replace native journal code.

Tagged packaged documents retain their original preparation snapshot. This nonpackaged publication record supplies later evidence without moving the tag or replacing accepted payloads.
